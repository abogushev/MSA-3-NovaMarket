### <a name="_b7urdng99y53"></a>**Название задачи: Просмотр истории покупок**
### <a name="_3bfxc9a45514"></a>**Функциональные требования**
После завершения доставки покупатель может вернуться в свой личный кабинет и увидеть историю всех покупок.
- В списке отображаются все заказы: когда они были сделаны, сколько стоили, каким способом доставлены.
- Для каждого заказа можно открыть подробную информацию: список товаров, их количество и цену, итоговую сумму, способ доставки и оплаты, финальный статус заказа (доставлен, отменён).
- Покупатель может скачать чек, оставить отзыв о товаре или заказать его снова.

### <a name="_u8xz25hbrgql"></a>**Нефункциональные требования**
Также учитывайте требования к отклику всех интерфейсов приложения!
### <a name="_qmphm5d6rvi3"></a>**Решение**
Воспользуемся EventStoreDB. Из kafka будем пересылать сообщения в EventStoreDB.
Стрим "события заказа":
    Для каждого заказа сформируем свой стрим order-{id} и пушим туда события с их мета-информацией:
    - создание: id, created_at, user_id, items(id, price), total_price, delivery_type 
    - оплата: payment_at, payment_type
    - смена статуса: «Ожидает оплаты»; «Оплачен, готовится к отправке»; «Передан в доставку»; «Доставлен»
Стрим (мат.представление) "снапшот заказа":
    Формируем стрим куда будет пушить снапшоты через проекцию цельной модели заказа по мере прихода событий
Стрим (мат.представление)"заказы клиента":
    Формируем стрим из заказов клиентов. Через проекцию после перехода заказа в терминальное состояние в стриме "снапшот заказа" пушим в стрим "заказы клиента" последний снапшот заказа
    При запросе истории заказов бекенд обратиться прочитает весь (или постранично) стрим "заказы клиента" 

**Недостатки, ограничения, риски**
- при большом кол-ве событий проекции могут обрабатываться медленнее

**Альтернативы**
1) Отказаться от мат.представлений и использовать простую комбинацию консюмера стрима "события заказа" и NoSQL по типу Сasandra. Создаем консьюмера, который подписывается на стрим, ожидая когда в стрим попадет терминальное событие заказа ("доставлен" или "отменен"), вычитывает весь стрим по товару, создает представление и пушит в Casandra. Чтение истории происходит запросом в Casandra, где шардирование по user_id.
   Плюсы:
      - убираем нагрузку от процессов проекций мат.представлений
      - не храним в EventStoreDB данные от мат.представлений, храним только "сырые" события 
      - Сasandra более надежный и масштабируемый инструмент для большого объема данных
   Минусы: 
      - шардирование по user_id может привести к дизбалансу объема хранимых данных на ноде
2) Сделать как в варианте выше, но использовать ElasticSearch вместо Casandra
   Плюсы:
      - более гибкий механизм поиска, что позволило бы делать фильтрацию или поиск по истории заказов
   Минусы:
      - менее надежный источник при записи

Итог:
    Пока можно обойтись только EventStoreDB т.к. его данными можно воспользоваться не только для истории, но и для аналитики, аудита и других бизнес-процессов
    Но при росте объема данных стоит комбинировать различные хранилища и использовать под каждую задачу свое: 
    Postges для обработки текущих заказов, ClickHouse для аналитики, ElasticSearch для покупателя для отображения истории и поиска по заказам, Redis как кеш самых новых и активных заказов (в купе для подстраховки ElasticSearch, чтобы текущий заказ был как можно более актуальным) 
    Данные в эти хранилища поступают из kafka кластера
    EventStoreDB можно либо убрать вовсе, либо оставить ему задачи аудита или менее критичные для бизнеса сценарии
